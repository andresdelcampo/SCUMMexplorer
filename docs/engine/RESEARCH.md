# SCUMM format and tool research

Research checked 23 September 2026. The goal is to reuse validated format knowledge while keeping SCUMMexplorer's domain model and UI independent from binary details.

## Existing explorers and parsers

- [SCUMM Revisited](https://quickandeasysoftware.net/software/scumm-revisited) has broad image, background, costume, audio and script features across several public versions. Its own page says versions 3 and 5 were unfinished and lack features present in version 2. It remains a valuable feature reference, not a dependable parser dependency.
- [SCUMM Explorer by Enrico Rolfi](https://erolfi.wordpress.com/scumm-explorer/) was a Mac-focused viewer/extractor which could display images, play sound/music, disassemble scripts and dump unsupported blocks. Its author notes platform-specific data differences and points to SCUMM reverse engineering/ScummVM as prior knowledge. Source code is linked from that page; its license and relevance to DOS LOOM need review before reuse.
- [ScummAtlas](https://github.com/ktzar/scummatlas) is the closest conceptual precedent: a parser and HTML atlas intended to make SCUMM games understandable. The author described room-level views with hotspots, objects, scripts and z-planes. Its published scope is mainly v5, with only partial v6 support, so it does not directly cover this v3 LOOM target.
- [ScummKit](https://github.com/michaelborgmann/ScummKit) has a historical ScummViewer background-rendering prototype and partial resource/room handling. The current project is Swift and focused on v5; its README says v4 and other versions remain experimental. Its prototype is useful for renderer/UI concepts, not a mature v3 backend.

## Technical references

- [ScummVM SCUMM engine source](https://github.com/scummvm/scummvm/tree/master/engines/scumm) is the strongest maintained implementation reference. Its [v3 resource reader](https://sources.debian.org/src/scummvm/2.7.0%2Bdfsg-1/engines/scumm/resource_v3.cpp/) confirms the `00.LFL` magic `0x0100`, a global-object table, and byte-sized directories with little-endian 16-bit resource offsets; non-room resources also carry container-room numbers. `resource.cpp` shows the numbered `.LFL` convention and small-header offset handling. The current Core reader is independently written to this observed layout; it does not copy ScummVM code.
- ScummVM's [v3](https://github.com/scummvm/scummvm/blob/master/engines/scumm/script_v3.cpp), [v4](https://github.com/scummvm/scummvm/blob/master/engines/scumm/script_v4.cpp), and [v5](https://github.com/scummvm/scummvm/blob/master/engines/scumm/script_v5.cpp) handlers and [resource string loading](https://github.com/scummvm/scummvm/blob/master/engines/scumm/resource.cpp) identify opcode operands and inline text boundaries for the old-v3 DOS LOOM target. The disassembler is independently written. It follows recognized control-flow paths and reports decode issues per path.
- The [ScummVM technical reference](https://wiki.scummvm.org/index.php?title=SCUMM/Technical_Reference) is a useful index, though the wiki was intermittently unavailable during this pass. Check the relevant resource pages before decoder implementation.
- [SCUMM Tutorial 0.1](https://tandell.com/misc/SCUMM-Tutorial-0.1.pdf) preserves historical development/debugger terminology and gives context for rooms, objects, scripts and z-planes. It is not a complete binary specification.
- [ScummVM LOOM detection and source](https://github.com/scummvm/scummvm/tree/master/engines/scumm) should be consulted to distinguish DOS EGA v3 from other LOOM editions; executable and resource-index signatures matter. The current scanner requires the DOS LOOM file profile plus a valid v3 index before reporting v3. LOOM cannot be identified solely from an extension.

## Architecture decisions

1. Keep `Core` independent of WPF. Model game, room, object, costume, script, sound and raw resource records in domain terms.
2. Put release detection and format-specific LFL/index readers behind Core interfaces. Detection should report confidence/evidence and avoid calling an inferred version confirmed.
3. Keep a format provider responsible for translating bytes into room backgrounds, palettes, objects, masks and scripts. The desktop layer should only display typed results.
4. Preserve the unmodified game files; reading should be non-destructive. Do not bundle game data.
5. Reuse ideas and cite research. Do not copy GPL implementation code into this project without deciding whether that license is acceptable. ScummVM and ScummKit are GPL-licensed projects; reference use and code reuse are different choices.

- The supplied DOS LOOM `00.LFL` and numbered rooms are XOR-FF encoded. Decoding the index yields the `0x0100` old-v3 magic; the old-v3 directory supplies room ordinals and offsets. The room header supplies image width and height at bytes 4-7 and the background offset at byte 10. The background begins with a length and a 16-bit offset for each eight-pixel strip.
- `LoomEgaRoomDecoder` reads the background strips into indexed pixels. The WPF preview uses the standard DOS EGA palette. The decoder was run against all indexed room files in the supplied LOOM folder; a flat-colour room is valid.
- Old-v3 room depth masks follow the background block. Their table has one 16-bit relative offset per eight-pixel strip; zero denotes an empty strip, and nonzero entries point to row RLE data. The decoder expands these one-bit masks to room pixels, and the preview can highlight them. This was checked across all 76 indexed room files, including empty mask data in `01.LFL` and marked pixels in `02.LFL`, `28.LFL`, `33.LFL`, and `41.LFL`. The layout and run encoding were cross-checked against ScummVM's [old-v3 room setup](https://github.com/scummvm/scummvm/blob/master/engines/scumm/room.cpp) and [mask decompressor](https://github.com/scummvm/scummvm/blob/master/engines/scumm/gfx.cpp#L2883-L2905); the implementation is independently written. These room depth masks are distinct from masks used inside object images.
- The old-v3 room object directory contains parallel image and code offsets. Image-less entries can repeat the next image offset, so the image belongs to the final entry in each repeated run. The Core directory reader retains valid code records even without separate images; it exposes local index, object ID, bounds, parent requirement, walk-to point, direction and asset offsets. Image strips use the same EGA compression as room backgrounds. The `00.LFL` global-object table gives state zero for the sampled LOOM room objects. The preview now starts from those index states and allows inspection of stored images by exact rectangle. Its background step is object state zero, regardless of pixel colour. This removes the manually selected Room 33 state, the Room 01 exception, the `(0,0)` exclusion, and the black-pixel/filled-background guesses. Entry scripts, script-driven positions, and animation are not yet reconstructed, so the preview is not a first-visit screenshot.
- Indexed DOS LOOM script resources are XOR-decoded, then bounded by their four-byte old-v3 resource header and its declared length. The desktop view follows recognized control-flow paths, including both arms of conditional branches, and reports decoded bytes and unresolved paths per script. It recognizes variable/direct parameter flags, relative branches, nested actor/room operations, and bounded inline SCUMM strings. A resource with an impossible length is reported as invalid. This disassembler does not execute bytecode or claim a first-visit state; the [release coverage report](../archive/LOOM_SCRIPT_COVERAGE.md) records the measured scope.
- The old-v3 costume header points to per-limb frame tables, animation commands, and direction/frame pose records. Format `0x58` cels use a 12-byte geometry and movement header followed by Byle RLE pixels. The preview resolves those records into static, transparent EGA images and honors the costume's transparent palette index and stored facing; it does not advance animation or infer a character's in-game state. These structures are cross-checked against ScummVM's [costume loader](https://github.com/scummvm/scummvm/blob/master/engines/scumm/costume.cpp#L388-L451), [pose and cel handling](https://github.com/scummvm/scummvm/blob/master/engines/scumm/costume.cpp#L547-L603), [pose command decoder](https://github.com/scummvm/scummvm/blob/master/engines/scumm/costume.cpp#L673-L743), and [Byle RLE decoder](https://github.com/scummvm/scummvm/blob/master/engines/scumm/base-costume.cpp#L273-L410). The implementation is independently written.
- The implementation follows the format behavior in ScummVM's [old-v3 index reader](https://github.com/scummvm/scummvm/blob/master/engines/scumm/resource_v3.cpp), [room setup](https://github.com/scummvm/scummvm/blob/master/engines/scumm/room.cpp), and [EGA strip renderer](https://github.com/scummvm/scummvm/blob/master/engines/scumm/gfx.cpp). It is independently written and does not copy ScummVM code.

## Parser work remaining

- A source-backed relationship index now connects old-v3 resource container entries, room-local object records and entry-script pointers, and literal targets in recognized script instructions. Its links retain file offsets and leave dynamic or undecoded references unresolved; this static index does not prove that a script branch or room transition is reachable.
- Compare representative room pixels with an independent renderer for this exact LOOM release.
- Compare representative script paths against an independent decoder for the supplied DOS LOOM release. The current path scan and ScummVM-source operand checks are recorded in the [exploration audit](../archive/EXPLORATION_AUDIT.md); independent output comparison remains useful. DOS LOOM costume resources render stored static poses from their limb masks, cel tables and Byle RLE pixels; this is not game-script animation.
- Only after opcode coverage is adequate, reproduce a new game's first visit to each room by executing startup, global and room-entry scripts along a specified route; carry their variables, object states, owners, positions, parent requirements and timing. Stop and report unresolved state when unsupported opcodes or path-dependent conditions occur. A game-state dropdown is useful once those states are reproducible from game data; do not invent named presets from image order.
- Add user-facing room names only where game data or a reviewed reference establishes them. Mark inferred labels as inferred.
