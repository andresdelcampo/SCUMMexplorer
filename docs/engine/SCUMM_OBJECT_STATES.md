# SCUMM room object states

Reconciled 8 October 2026. This reference separates the current interaction/rendering contract from the original old-v3 format evidence. LOOM EGA and CD/VGA use edition-specific data providers; the v3 byte offsets below do not apply to VGA archives. Current capability and remaining comparisons are in [the plan](../CURRENT_WORK.md) and [CURRENT_WORK](../CURRENT_WORK.md). The complete early implementation record is preserved in [the historical snapshot](../archive/SCUMM_OBJECT_STATES_BEFORE_RECONCILIATION_2026-10-08.md).

The image directory is an asset directory. Geometry or image order cannot establish which images belong to a story transition. Reached script state, positions, parent requirements and draw order feed the renderer; unresolved behavior and display-only estimates remain explicit.

## Current interaction and session contract

- Maniac/Zak admin catalogs distinguish logical inventory items from scene representations. Index Pickupable metadata alone does not establish a separate retained item. A bounded, fully resolved native pickup closure may prove an alias only when it has no pickup/Pickupable effect, returns exactly one other same-name retained item to Ego and has resolved call/queued-sentence dispatch. Unknown values, source changes, cycles and incomplete code retain the candidate. Neither classification nor display changes live slots or owners. Genuine equal-name resources remain separate. [18 October identity evidence](../../.verification/zak-item-identities-20261018/README.md).
- Recipient pictures are detached native costume frames. Native showActor frame initialization runs in private limb state; an uninitialized costume requires a unique nonzero literal source assignment. Rendering these copies changes no live actor, input, story or inventory state. Maniac's party eligibility comes from native selected bindings and post-Start actor placement. [Character evidence](../../.verification/status-character-art-20261018/README.md).
- In Interactive mode, a single click sends source input that walks/uses through the game's scripts; a double click also looks. Playback advances actors, camera, messages and scripts, and follows reached room loads. Inspection mode cycles stored artwork without changing the persistent session.
- Source touchability and responses govern navigation. A closed/untouchable exit cannot be forced through an ordinary click or doorway fallback. Advanced catalog browsing can still open a room as a disclosed exploration arrival. [Portal validation](../../.verification/portal-state-20261008/README.md).
- Single scene picks preserve the running session; stated sequences start fresh. Rooms normally use their earliest source entry state until reached scenes establish later state. On 8 October the user approved reviewed source prerequisites for direct late-room catalog starts. The fingerprinted English Room 46 recipe runs missing real scenes, preserves ghost/restored state and cancels the visit on failure. [Catalog return validation](../../.verification/catalog-return-20261008/README.md).
- Object state comes from the index and reached script operations. `SetState` changes the specified object; `DrawObject` applies source position changes and clears exact-bound peers. Parent-state requirements and room ownership govern active selection. Painting uses directory redraw plus the recorded draw queue; hit selection respects live script state.
- Display gap filling and provisional artwork do not assign persistent game state. Costumes persist until source changes them. No room-specific renderer preset, fabricated story flag or geometry-derived story transition is justified.
- A verified first visit means the settled state reached through the earliest normal game route. Catalog arrivals, direct verbs, explicit staff/note edits and seeded choices remain preview assumptions. Current bounded coverage does not prove every native input route, actor picture or audiovisual detail.

## First visit of a room without LOOM's session (old bundle, S5, 14 October 2026)

For a game with no game-specific session (Indiana Jones and the Last Crusade EGA) the first visit of a room is built by the generic session (`ScummRoomFirstVisit`):

- **Route.** The first playable room is the boot's own state. Any other room is entered **without playing the route to it** (ScummVM's debugger `room N` does the same: `startScene`), from the state the boot left, with the ego brought in as one decoded `loadRoomWithEgo` into the room would bring it (a seeded, labelled pick among the distinct placements, those found in the previous room's own code first). Nothing is written to the story state; the visit is a state preview, never a reached outcome.
- **Settled.** After the entry hooks, the entry script and the child scripts have started, frames are played until nothing has changed for 90 frames (no cutscene, message or movement, and no change in object states, positions, actors' rooms and positions, costumes, palettes or the camera), or until a script leaves the room (the state at the last frame in the room is kept), or a limit of 2400 frames. An object whose state or position changes four times within 240 frames is an **ambient animator** (a crowd, a flame): it does not keep the room from settling and is shown in the phase of its loop the room was in when the rest began. A room whose own scripts never rest within the limit says so (outcome "frame limit").
- **No pixels are filled.** A gap that remains after a correct run means missing script behaviour, not a reason for a room-specific fill.
- **Hotspots** follow `findObject` (`object.cpp`): an object is skipped when it is untouchable (class 24); its parent chain must be in the required states; its own state does not matter. The explorer also leaves out objects the room does not own and objects at 0, 0 (off the scene).

### v4 (several disks, S5 MonkeyFloppy, 15 October 2026)

- The same rules apply to a v4 game: the index (`000.LFL`) gives the starting states, the disk that holds the room gives its picture, objects and scripts (`ScummV4DiskSetDataSource`). The class numbers are the small-header ones (ScummVM `putClass`/`getClass` translate class 32 to 24 for `GF_SMALL_HEADER` games, which include the v4 floppies), so untouchable is class 24 as in v3; the scripts set it with `setClass obj, [0x98]` and clear it with `[0x18]`.
- **A room the game only loads under pseudo room numbers** (see [pseudo rooms](SCUMM_SCRIPT_MAP.md)) is visited under the number a decoded `loadRoomWithEgo` into it uses (arrivals from the room's own code, which lead from one pseudo room to another, count only when no other exists); without such an arrival, under one of the numbers the game's `pseudoRoom` instructions give it (seeded, labelled). Visited under its own number its entry script would draw none of its layouts.
- An arrival from the room's own code is never the first visit when another arrival exists (a first visit comes from elsewhere).

## v1/v2 held inventory and explicit status choices (S8, 18 October 2026)

Native `object.cpp::putOwner` stores ownership separately; `script_v2.cpp::o2_actorOps` suboperation 3 retains an actor name. Reached names are now retained by the v1/v2 executor. In the status reader, native input-script assignments to ego followed by `actorFollowCamera` establish selected-party variable bindings. Where no such bindings exist, the source-written engine player range supplies candidates. Own-edition facts belong in the Maniac/Zak script maps; an unresolved identity is not guessed.

Native `script_v2.cpp::o2_doSentence` distinguishes ordinary object slots from special (`0xFD`) and background/special (`0xFA`) handlers. A resident special handler can loop while the player has control; it is not by itself an unfinished player action. The status guard rejects executing code, input/sentence work, ordinary foreground object slots, queued input, movement, dialogue and cutscenes. Source reviewed 18 October 2026; the slot-lifecycle regression and retained failed all-slot guard are in the [S8 record](../../.verification/maniaczak-state-20261018/README.md).

The original S8 editor changed only an already-held item's owner, preserving its native slot and retained room/code, state/classes, other items, actors and words. This historical restriction is **superseded by the user's admin clarification in §12 of REQUIREMENTS**. It was an editor scope choice, not a native engine restriction. The session identity, frame generation, exact relevant signature and revision still protect atomic batches and conservative undo; a playback frame invalidates undo, so the modal pauses Play.

## v1/v2 explicit admin inventory grants (18 October 2026)

The admin API uses native inventory storage without running pickup/story scripts. The source-derived catalog combines indexed Pickupable flags, script writers and pickup calls, including active-object helper calls; ambiguous source rooms are not chosen by scan order. `o2_doSentence` special resident handlers (`0xFD`) do not bind their own object as an ordinary foreground sentence target. The [Core evidence](../../.verification/maniaczak-admin-inventory-20261018/README.md) records source review, candidate coverage and native retained-code checks.

Native inventory has a separate slot array and retained code-room identity. Grants reserve a free slot, keep the item's source room/code/preposition, set its owner and the native pickup intrinsic/untouchable bits while preserving other flags. Transfers preserve the existing slot and metadata. Validate every resource, recipient and available slot before writing; Undo restores dictionary absence as well as values, membership, flags and exact slot layout. No inventory callback, puzzle score or unrelated story variable is synthesized. This is an explicit admin state choice, not native pickup/Give gameplay. Source: ScummVM `object.cpp` inventory storage and `script_v2.cpp::o2_pickupObject`, reviewed 18 October 2026; implementation and source-based tests are linked in the evidence record.

## Historical old-v3 format evidence

The following byte offsets, object IDs and counts belong to the supplied Spanish EGA audits of 27 September. They remain source evidence for that edition, not a fresh English/VGA inventory.

1. `00.LFL` starts with the `0x0100` signature and a global object count. Each object has three class bytes and one packed owner/state byte. The state is the high nibble. In the supplied LOOM index, objects 476–499 and 545–554 all have packed byte `0x0F`: owner 15, state 0. Thus the index alone would draw none of these images.
2. In old v3 rooms, byte 20 is the number of local objects. Image offsets and code offsets start at byte 29. The code records identify objects and their dimensions, position, parent, required parent state, walk-to coordinates, and facing direction. Some records have no distinct image; a run of entries can share an image pointer, with the final entry owning that image. `ScummRoomObjectDirectory` retains all valid code records, while `ScummRoomObjects` decodes only image-owning records.
3. The room entry script offset is the little-endian word at room bytes `0x1B–0x1C`. For the supplied rooms it is 31,388 in `28.LFL` and 14,750 in `33.LFL`. SCUMM runs global entry script, room entry script, then a second global entry script where configured. Those scripts can start others, branch on variables, and change object states.
4. An object is drawn when its state is nonzero and its parent state requirement is met. A room redraw (`drawRoomObjects`) paints active local objects in reverse room-directory order, so an earlier directory object covers a later overlapping one. `drawObject` does not paint immediately: it queues the object, and queued objects are painted on top of the redraw in call order (`processDrawQue`). `setState` marks the object's area dirty, which causes a redraw and clears that queue. Close-up faces (LOOM Rooms 56, 58, 86 and others) depend on this: the face image has colour-0 cut-outs that the eye or mouth images drawn after it fill, so directory order alone leaves black gaps. SCUMM `drawObject` explicitly clears the state of objects with **exactly** the same x, y, width, and height, then sets the requested object's state. `setState` changes only the specified object. `drawObject` can also move the requested object before comparing bounds. Neither rule says that overlapping images, shared bottom edges, or adjacent object IDs form variants.


## Display-only artwork estimates

The EGA selection implementation retains the following gap heuristic. It affects displayed artwork only; supported source state remains authoritative.

When an incomplete room visit leaves a **gap**, `FillGaps` closes it. A gap is a stored-image rectangle that is at least 90% colour 0 in the composite while the ring of pixels around it is at most 60% colour 0, and that has a stored image with at most 60% colour 0. The largest gap is filled first, so a container is chosen before the inserts in its cut-outs. It is filled by repainting an active image, else by applying the whole highest-priority `ScummSceneDrawBatches` batch that includes one of its images (a seeded pick among ties, seed = room number), else by a seeded random stored image. Batch priorities are 3 for the opening frame (the draws right after a script's *first* literal load of that room), 2 for the room entry script and 1 for all other scripts; a later load of the same room in the same script is a return, not an opening. When the visit leaves **no** script-visible artwork at all, the viewer also chooses a reproducible provisional image at each nonoverlapping position (`ShowUnresolvedArtwork`). Script-visible images take priority over every estimate; no room ID or object ID is hard-coded. These estimates exist only in the displayed room selection, not in the persistent SCUMM session. The UI labels their count and individual object entries. They are a useful early view when the interpreter cannot reach a state, but their combination is not proven by the game. Subsequent script actions replace this provisional view with reached state. The selection checks decoded parent-state requirements in session mode, so a child image is not rendered unless its parent chain matches.

## SCUMM v1/v2 first-visit state (17 October 2026)

The generic first-visit runner reads the old index and background through the v1/v2 data source, then runs boot, entry hooks and child scripts. Catalog arrivals remain the labelled state previews of R-5.3a; a required player choice is supplied outside the engine by an explicit reviewed input recipe. No index-only picture is called a reached first visit.

- `object.cpp::drawRoomObjects` uses intrinsic state bit 8 for visibility; parent conditions compare that bit, not the entire state nibble. `findObject` rejects old state bit 2 (untouchable). The first-visit image selection and hotspot eligibility retain those version-specific rules.
- Repeated global object IDs can have separate stored images in one room. Directory redraw retains each image and its directory order; global state remains shared. Script object lookup selects the last matching directory entry (`getObjectIndex`). Queuing that last image retains earlier directory images. The repeated images of Zak Room 19 are covered by the family audit rather than silently dropped; both have no parent. Duplicate IDs with differing parent conditions remain an unverified general case.
- `pseudoRoom` mappings and arrivals are read from the disassembly's numeric operands, accepting the v2 hexadecimal spelling as well as the later decimal spelling. A pseudo-room choice remains a labelled arrival assumption, not a played route.
- Old literal arrival walks use eight-pixel x units and two-pixel y units. A catalog visit converts both nonnegative operands to session pixels, matching the executed opcode; negative sentinel operands suppress the walk. The v2 object's walk point overrides the initial entry placement as the native `o2_loadRoomWithEgo` does.
- v1/v2 background scripts can change object flags in unloaded rooms. The preview's settling signature watches current-room object state and positions while the complete persistent snapshot retains remote changes. The quiet-frame and bounded ambient rules remain those of R-5.3a.

Engine sources: ScummVM `engines/scumm/object.cpp`, `script_v2.cpp`, `room.cpp`, read 17 October 2026. The gap detector measures black regions under stored image rectangles; an unchanged black region in native background artwork is evidence to investigate, not permission to activate an object or fill pixels. Counts and comparison limits are retained in [the Maniac/Zak S5 checkpoint](../checkpoints/20261017-S5-ManiacZak.md).

## Historical supplied-EGA script evidence

- In `33.LFL`, the entry script starts at decoded offset 14,750. At 14,837 it tests bit variable `0x8D81`. One branch draws objects 551–554; the other draws 547–550. Later bytecode draws 545 and 546, whose exact-size peers are cleared by `drawObject`. This explains how the former manual arrangement could arise, but the branch value and the point at which the room should be sampled still depend on game execution. The script also starts other scripts and has multiple frame breaks. A list of image IDs alone is not a verified first-visit snapshot.
- In `28.LFL`, the entry script starts at decoded offset 31,388. Its early loops clear 483–489 and 476–482, then set 490–496 to state 1. Later drawing sequences for 483–489 and 476–482 are interspersed with actor commands and frame breaks. Thus 490–496 are a script-proven coherent early frame, but the stable post-entry view still requires running the remaining sequence. Selecting one image per black area would mix these sequences without evidence that they coexist at the same time.
- All 76 indexed rooms have embedded entry scripts. The sampled room objects in the global index start at state zero. A room-wide first-visit view therefore requires following script execution and persistent game variables; it cannot be recovered by initializing every object from the index or by filling black pixels.

## DOS SCUMM v1/v2 lighting and actor palette persistence (18 October 2026)

Source: ScummVM `gfx.cpp::drawFlashlight`, `scumm.cpp` v2 constructor/render order, `costume.cpp::ClassicCostumeRenderer::setPalette` / `byleRLEDecode_C64`, and `actor.cpp::Actor::setActorCostume`, read 18 October 2026. [Lighting record](../../.verification/maniacenhanced-fidelity-20261018/README.md) pins fetched source hashes; [palette record](../../.verification/zakclassic-fidelity-20261018/README.md) retains reached contexts. These statements apply to DOS v1/v2, not later renderers.

- Room light bit 2 exposes the composed background/objects; without it the front background is black. Bit 4 restores a pointer-centered flashlight window from that composition. Snap, viewport clipping and asymmetric nibble corner masks follow separate native v1/v2 tables. Default dimensions are 6x4 eight-pixel strips, inherited by v1; reached script instructions can resize them.
- Room colour mapping precedes lighting. Actors are drawn afterward, with native colour mode bit 8. V1's dark pixel codes use its native colour-11 remap/black; v2 uses gray 8 with the source black/entry-12 behavior. Actor geometry, ownership and story state are not changed by rendering. A full room preview and live Play use the same composition and apply the display palette once.
- V1 actor costume changes retain every dynamic palette slot. V2 and the existing later old-bundle path retain their identity reset. A costume may therefore appear in multiple native contexts with different colours; a reached context does not turn a global costume card estimate into a universal palette rule.
