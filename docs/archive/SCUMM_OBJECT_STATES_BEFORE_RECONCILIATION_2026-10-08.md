# Old v3 SCUMM room object states

Technical reference. See the [LOOM EGA product plan](../LOOM_EGA_PLAN.md) for current priorities and progress; this document records the rendering and state contract.

The object image directory is an asset directory, not an animation or variant table. A correct first-visit room view must use object state produced by the SCUMM interpreter. Geometry or image order cannot establish which images belong to a transition. The explorer now runs a bounded subset of startup, room, and object-verb scripts in a persistent session, with unresolved behavior shown explicitly.

## Verified format and engine rules

1. `00.LFL` starts with the `0x0100` signature and a global object count. Each object has three class bytes and one packed owner/state byte. The state is the high nibble. In the supplied LOOM index, objects 476–499 and 545–554 all have packed byte `0x0F`: owner 15, state 0. Thus the index alone would draw none of these images.
2. In old v3 rooms, byte 20 is the number of local objects. Image offsets and code offsets start at byte 29. The code records identify objects and their dimensions, position, parent, required parent state, walk-to coordinates, and facing direction. Some records have no distinct image; a run of entries can share an image pointer, with the final entry owning that image. `LoomRoomObjectDirectory` retains all valid code records, while `LoomRoomObjects` decodes only image-owning records.
3. The room entry script offset is the little-endian word at room bytes `0x1B–0x1C`. For the supplied rooms it is 31,388 in `28.LFL` and 14,750 in `33.LFL`. SCUMM runs global entry script, room entry script, then a second global entry script where configured. Those scripts can start others, branch on variables, and change object states.
4. An object is drawn when its state is nonzero and its parent state requirement is met. A room redraw (`drawRoomObjects`) paints active local objects in reverse room-directory order, so an earlier directory object covers a later overlapping one. `drawObject` does not paint immediately: it queues the object, and queued objects are painted on top of the redraw in call order (`processDrawQue`). `setState` marks the object's area dirty, which causes a redraw and clears that queue. Close-up faces (LOOM Rooms 56, 58, 86 and others) depend on this: the face image has colour-0 cut-outs that the eye or mouth images drawn after it fill, so directory order alone leaves black gaps. SCUMM `drawObject` explicitly clears the state of objects with **exactly** the same x, y, width, and height, then sets the requested object's state. `setState` changes only the specified object. `drawObject` can also move the requested object before comparing bounds. Neither rule says that overlapping images, shared bottom edges, or adjacent object IDs form variants.

## Consequence for the preview

The bounded SCUMM v3 session feeds known object states and positions to the renderer. It runs the recognized parts of startup, room entry/exit, and directly selected object-verb scripts. During verb execution, a room change is applied only when execution reaches a room-load instruction. The separate possible-doorway buttons open their candidate rooms directly for exploration, without executing the originating verb or establishing its conditions. The input script, actor walking, some engine variables, and class-based hit selection remain unresolved, so the session does not claim a faithful first visit. Asset inspection is a separate mode that selects stored images without running game code.

Started scripts are child executions. If a child reaches an unsupported command, its uncertainty is retained but the caller continues through its own known instructions. This matters in Room 28: the entry script starts scripts 16 and 17, then reaches state writes for objects 476–482 on the current bounded path. Stopping the caller at the unresolved child formerly left those objects invisible. This does not establish the route-dependent choice of state for every visit.

`RoomObjectSelection.PaintOrder` reproduces this model: the directory-order redraw followed by the draw queue that the bounded executor and session record (`LoomBoundedScriptResult.DrawOrder`, `LoomSessionSnapshot.DrawOrder`). `Compose` paints it and `HitTest` uses the same order.

When an incomplete room visit leaves a **gap**, `FillGaps` closes it. A gap is a stored-image rectangle that is at least 90% colour 0 in the composite while the ring of pixels around it is at most 60% colour 0, and that has a stored image with at most 60% colour 0. The largest gap is filled first, so a container is chosen before the inserts in its cut-outs. It is filled by repainting an active image, else by applying the whole highest-priority `LoomSceneDrawBatches` batch that includes one of its images (a seeded pick among ties, seed = room number), else by a seeded random stored image. Batch priorities are 3 for the opening frame (the draws right after a script's *first* literal load of that room), 2 for the room entry script and 1 for all other scripts; a later load of the same room in the same script is a return, not an opening. When the visit leaves **no** script-visible artwork at all, the viewer also chooses a reproducible provisional image at each nonoverlapping position (`ShowUnresolvedArtwork`). Script-visible images take priority over every estimate; no room ID or object ID is hard-coded. These estimates exist only in the displayed room selection, not in the persistent SCUMM session. The UI labels their count and individual object entries. They are a useful early view when the interpreter cannot reach a state, but their combination is not proven by the game. Subsequent script actions replace this provisional view with reached state. The selection checks decoded parent-state requirements in session mode, so a child image is not rendered unless its parent chain matches.

Room backgrounds, room depth masks, local object records, object images and placement are available as graphics-first parsing features. The room depth mask is a separate walk-behind/occlusion layer; it is not an object-image mask and does not decide which item placeholder image belongs in the room. Indexed and embedded LOOM scripts have bounded control-flow disassembly, and the session applies reached state changes. The [27 September room audit](../../.verification/room-audit/validation.md) finds no remaining gap in any of the 76 rooms after filling. The views are still state previews, not verified first visits: no room's fresh visit is faithful, and gap fills are labelled estimates that make no game-state claim.

Room 28's 479 and 486 have equal bounds; 493 is taller. Room 33's bridge images also vary in bounds. Their relationships must come from script behavior, not their geometry. The disconnected bridge cannot be inferred as a universal initial state from these image records. The earlier Room 33 preset was a manual presentation choice and has been removed.

## Evidence from the supplied LOOM scripts

- In `33.LFL`, the entry script starts at decoded offset 14,750. At 14,837 it tests bit variable `0x8D81`. One branch draws objects 551–554; the other draws 547–550. Later bytecode draws 545 and 546, whose exact-size peers are cleared by `drawObject`. This explains how the former manual arrangement could arise, but the branch value and the point at which the room should be sampled still depend on game execution. The script also starts other scripts and has multiple frame breaks. A list of image IDs alone is not a verified first-visit snapshot.
- In `28.LFL`, the entry script starts at decoded offset 31,388. Its early loops clear 483–489 and 476–482, then set 490–496 to state 1. Later drawing sequences for 483–489 and 476–482 are interspersed with actor commands and frame breaks. Thus 490–496 are a script-proven coherent early frame, but the stable post-entry view still requires running the remaining sequence. Selecting one image per black area would mix these sequences without evidence that they coexist at the same time.
- All 76 indexed rooms have embedded entry scripts. The sampled room objects in the global index start at state zero. A room-wide first-visit view therefore requires following script execution and persistent game variables; it cannot be recovered by initializing every object from the index or by filling black pixels.

## Current preview and interaction contract

- `LflObjectStateReader` reads the high state nibble of each `00.LFL` global-object entry. The persistent session starts there and applies reached script operations across room visits; the inspection mode offers an isolated asset view. Neither is automatically the first-visit game view. The state model has distinct `SetState` and `DrawObject` operations; the latter applies any script position change before clearing only exact-rectangle peers. The renderer clips moved objects to the room bounds.
- Clicking an image area in either mode cycles: hidden/background → first stored image at the clicked rectangle → other stored images with **exactly** the same x, y, width and height in room directory order → room background, only when the decoded background behind that rectangle has no gap. Otherwise the cycle wraps to its first image. Without a decoded background, the index state must show that the position can be empty. Each shown image acts as a viewer `drawObject` call: it is painted on top, and gaps inside its rectangle (for example a face's eye and mouth cut-outs) are refilled from script batches as above. Hiding a container also hides the inserts that sit in its colour-0 cut-outs. The stored rectangle remains clickable after hiding, so the first image can be restored. Visible images take click precedence over hidden areas. These clicks change only the displayed room selection, not the persistent script session. Image clicks take priority over overlapping doorway hotspots so restoration always works; doorway buttons remain available, and clicking a doorway with no image still navigates. Script verbs are available from the hotspot list. A separate object-list selection can show an image with different bounds. This is a viewer interaction, not a claim that the game's scripts perform that transition.
- In session mode, a hotspot click chooses from its decoded local verb entries, respecting known room ownership and parent-state requirements. A sole verb runs directly; a static room destination is marked as possible until that bounded run reaches its room load. The action trace records the object ID, numeric verb, script offset, reached destination, and unresolved behavior.
- Distinct rectangles remain independent even if they overlap or share a bottom edge. The viewer does not swap several rectangles together. A future synchronized option needs script evidence that identifies the affected object IDs and the states changed together; the image directory alone is insufficient.
- `(0,0)` is a valid recorded coordinate and is no longer globally excluded. It may still be changed by a script. There are no room-number presets or title-screen exceptions in the selection logic.
- A first-visit view means the stable state reached from a new game through the earliest normal play route, after automatic room-entry scripts and their triggered animation have settled. For rooms reached later, this depends on the route, variables, inventory, and scripts already run. The current session reports unresolved branches, but cannot yet reproduce the full input and actor path. A game-state dropdown should use states established from the game rather than invented presentation presets.

Hotspot selection and session image selection both check parent-state requirements. `RoomObjectSelection.IsActive` follows the parent chain when room records are supplied; this check does not establish that the bounded session has resolved every required state. The supplied old-bundle format uses the same image pointer for every nonzero state of one object; here, state values control visibility, while alternatives are separate object IDs. Script-driven position changes and unresolved engine state must be accounted for before a view can be marked game-accurate.
