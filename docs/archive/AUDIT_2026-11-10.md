# Project audit, 10 November 2026

Asked by the user: are the implementations generic enough, where do the odd pictures come from (Indy in Maniac Mansion, a flying sheep in LOOM, a bouncing head at Indy 3's Grail knight), which steps are left, and which documents matter. Read, not run: the sources under `src/`, the documents, and the latest measurement (`.verification/scene-setup-20261031/*-run73.txt`). The plan that follows from it is in [ROADMAP](../ROADMAP.md).

## What is in good shape

- **The engine layer is game-free.** `Core/Scumm` (38,300 lines) names a game in one place, `ScummProfile.For`; the session, script executor, scene setup and renderers never test which game runs. `Core/Loom` is 6,650 lines, `Core/Maniac` 108.
- **Game Status has the right split.** One generic inventory window (`InventoryStatusWindow`) with a per-game schema read from the scripts (`ScummStatusSchema`: Indy 3's health, outfit, IQ awards, flags), and LOOM's own window for drafts and the distaff. A new game supplies a schema, not a window.
- **The App has a module seam** (`IGameModule`, `App/Loom/`), and every game-id test in the App is a LOOM test: no Maniac or Indy branches outside two party checks.

## Pitfalls

### 1. The window holds each game's state in about 150 loose fields (cause of "Indy in Maniac Mansion")

`MainWindow` is 6,032 lines in one file plus 25 partial files, with about 280 fields; roughly 150 belong to the open game (sessions, planners, caches, overlays, cues). Opening a game resets them one by one in `OpenGameFolder`, `ShowGame` and the module's `Reset`. The 9 November leak was one forgotten field (`_playBoot`). The audit found one more of the kind, `_startSetups` (LOOM's derived scene starts, never emptied; fixed with this audit), and three static caches keyed by folder alone, not by folder and language (`ScummDoorwayFinder.WalkVerbs`, `LoomDemoLooks`, `ManiacFirstVisit`).

**Fix:** one `GameContext` object that owns everything belonging to the open game; opening a game replaces the object. A field that is not in it cannot leak, and a new field cannot be forgotten. This is also the natural first cut of `MainWindow.xaml.cs`.

### 2. A scene's setup is judged by "it began", not by what it shows (cause of the head and, probably, the sheep)

`ScummCutsceneRun.Score` is `(Begun ? 10000 : 0) + rooms entered × 20 + lines`. The setup search tries candidate values one by one and in pairs and keeps the highest score. Nothing in the score, in `Measure`, or in the roadmap's percentages looks at the picture. Example, Indy 3 Room 82, Give Grail (run 73): the candidate that plays the ending (object 10, Room 94, 96 lines) ran into the frame limit, and the kept setup is "object 3 used with it, the hero comes in by object 861" (Room 83, 18 lines): another branch of the verb, with whoever object 3 is standing in the temple. The scenes "started at their cutscene" skip the code before the `cutscene` instruction and start with locals at 0, so an actor that code would have dressed or placed keeps whatever it had.

The sheep was not traced to an instruction. The likely sources are the same family: Interact on objects "not yet present" (R-8.38) and actor placements (`ActorX`, `WalkBox`, `ActorNear`, `ActorRoom`) that stand an actor somewhere without the room script that would have placed it.

**Fix:** measure the picture. Cheap checks at the end of every measured scene, reported per game as a percentage and listed in Advanced: an actor in the room whose costume no script of this run set; an actor outside every walk box of the room (allowing for elevation the scripts set); an actor still playing its initial frame while it moves; a scene whose first 50 frames show no actor, line or object change. Use them first as a list for the user (30 suspects instead of 1,400 scenes), then as a penalty in the score.

### 3. The setup search keeps growing by one script idiom at a time

`ScummSetupKind` has 25 kinds, most added for one scene of one game and then offered to all. Each is generic in form (no room numbers), but the returns are falling: the last batches moved Indy 3 from 7 to 4 scenes of 81. Work item 1's remainder is by its own description one-offs.

**Change of direction:** stop adding kinds for the last 3 to 8 percent. A scene that still shows nothing leaves the Normal list (R-1.13 already says content that is not ready is simply not offered) and stays in Advanced, labelled.

### 4. Replacing LOOM English's hand-validated catalog is the riskiest open item and blocks nothing

Roadmap item 2b ends with the shared engine replacing the 328 reviewed replays. They are the only ✅ in the Cutscenes column and the product's reference. The comparison already says what the engine can do (238 of 238 begin, 222 within 10% of the length); switching the reference to it trades a validated list for a derived one to save data that is already written.

**Change of direction:** keep the catalog as shipped data and as the answer key for the engine. Do not make the switch a release condition; revisit after the release.

### 5. Generic features live under LOOM names

Readable scripts (`LoomScriptPresenter`), names (`LoomGlossary`, used by every game through `GameModuleBase.CreateNames`), Game Texts (`LoomTextExtractor`) and the usage index (`LoomUsageIndex`) serve every game but sit in `Core/Loom`, which `Core/Scumm` cannot see. Roadmap item 3 (names for the other games) will add more non-LOOM code there. Move the game-free halves to `Core/Scumm` (`Text/` or `Analysis/`) before item 3; leave LOOM's reviewed names in `Core/Loom`.

### 6. Smaller

- `ScummProfile.For` tests the family 20 times. `HasFirstVisitScenes` and `PlaysThroughVerbs` are now true for every family but LOOM and can be one line each.
- `Core/Maniac` is a fourth layer the layout notes did not mention (now in CLAUDE.md).
- `VAR_VIDEOMODE` 19 for every v4 game (already open under Monkey Island 1).

## Documents

- **REQUIREMENTS.md is 191,000 characters for 260 rows.** 114 rows are the user's rules (95,600 characters, 840 each on average; the longest cell is 4,200), 106 describe the code as it is (window widths, exact strings), 17 are proposals for Play, which the 31 October scope put last. Rules, implementation names, dates and checkpoint stories share the same cells. 80 of the ids are cited from the code (311 places), so rows cannot simply be deleted. Done the same day on the user's yes: REQUIREMENTS is now the rules only, one or two sentences each (18,700 characters), and the full file is frozen as `REQUIREMENTS_DETAIL_2026-11-10.md` so every cited id still resolves.
- **`NEXT_SESSION_PROMPT_MANIAC_ZAK.md` was a stack of handoffs ending 23 October**, for a separate track that has not run since; Maniac Mansion's scenes have been worked in the main track since 1 November. Archived with this audit; its open items were already in the roadmap.
- **ROADMAP.md**: the work list had grown cells of 250 words. Rewritten with this audit as "The way to a release".
- **`.verification/`** holds 3,222 of the repository's 3,851 tracked files and 553 MB on disk; `scene-setup-20261031/` alone has 969 run files. Not touched (the changelog links into it). Suggested: keep each game's last two runs, delete the others.
- `docs/archive/` was left as it is: live documents still link to its 8 October snapshots.
