# LOOM EGA exploration plan

## Product direction

Make the supplied DOS *LOOM* EGA release feel like a place to explore: rooms and their original artwork lead; visible exits and objects invite clicks; meaningful draft actions can change the displayed world; original sound is available where the game data supports it. Keep source details available on demand so the main view remains understandable without SCUMM knowledge. Later, add scene playback and a discoverable, evidence-backed guide to secrets.

The target view is a large room canvas. Clicking an object opens a compact contextual card with source-supported draft choices, before/after state thumbnails, and reset or undo for previews. Small sound controls sit near the room; a room picker or map helps browsing. A supported scene can be played or replayed. The resource tree, raw IDs, and script evidence stay collapsed until requested. Unsupported actions explain the missing condition briefly instead of presenting an inert click target.

This is a product plan, not a claim of complete gameplay emulation. The [exploration audit](EXPLORATION_AUDIT.md) and [object-state notes](SCUMM_OBJECT_STATES.md) remain the technical record. Their 25 September 2026 counts and checks are historical audit results; the 25 September planning pass did not repeat runtime validation. ## Evidence and status rules

For each exit, object action, draft result, state change, sound cue, and eventual scene or secret, link the LOOM EGA resource, script, instruction and condition that support it. Describe what the source establishes and what remains inferred. A decoded conditional branch or room-load instruction is a **possible** outcome; direct invocation of a verb is an **exploration action**; a partial bounded session is a **state preview**. Call something gameplay execution only when the necessary input selection, state, conditions, sequencing, and resulting changes are actually modeled and verified. Do not fill gaps with room-specific behavior exceptions or erase a verified source glitch.

Keep progress here rather than rewriting reverse-engineering notes. Use `verified` for a source-backed behavior demonstrated in the app, `preview` for an intentionally partial state, `unresolved` for missing evidence or execution, and `deferred` for later scope. After each small milestone, update the relevant row above, the acceptance checks, the evidence link, and the next single task.
