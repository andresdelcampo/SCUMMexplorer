# Audit, 27 September 2026: LOOM EGA rendering gaps and Indy3 EGA dialogue choices

Scope: the reported black gaps in LOOM EGA rooms 56, 58 and 87, the Room 17 patches that are already known, and the missing player dialogue choices in *Indiana Jones and the Last Crusade* EGA. This is a source and data audit. **No code was changed.** The findings come from:

- decoding the supplied `Games/loom` and `Games/indy3/EGA` files with an independent Python reader and the ScummVM `descumm` tool;
- the current ScummVM engine source (`engines/scumm`);
- reading `SCUMMexplorer.Core` and `MainWindow.xaml.cs`.

The .NET app was not built or run during this audit, so behaviour attributed to the app is a code reading. Evidence files are in [`.verification/archive/audit-2026-09-27/`](../.verification/archive/audit-2026-09-27/).

## Overall project state (short)

- **Parsing is broad and well evidenced.** Backgrounds, object images, depth masks, costumes, sounds (PC speaker and AdLib), the text gallery and a bounded session all work. The docs are careful about "possible" vs "reached".
- **Rendering is the weakest part.** The object layer is a state snapshot painted in one fixed order. The engine instead shows a persistent back buffer: redraws paint every active object in directory order, and `drawObject` calls then paint over it in the order they were made. Findings 1–3 all come from this gap.
- **The disassembler has no game variants.** It is written against LOOM. Indy3 needs per-game operand rules (finding 4).
- **Dead code:** in `LoomScriptReader.cs`, `0x3B`/`0xBB` is matched as `getActorScale` at line ~361 before the `waitForActor` case at line ~437, so the second case never runs. This is harmless for LOOM, which never emits `0x3B`, and wrong for Indy3.
- **Housekeeping:** many build outputs are committed under `src/*/Exe/` and `.verification/*/obj/`. The main window code (`MainWindow.xaml.cs`, about 2,000 lines) holds most of the UI logic.

## Finding 1: rooms 56 and 58 (eyes)

**Data.** In Room 56, face 779 is 48×56 at (80,40). Its pixels under the eye rectangle (88,56,40,8) are 100% colour 0. The eye images 782–784 fill exactly that rectangle. Face 781 is a complete face with no cutout, and 780 is the top half of the face. The background is also colour 0 under the whole face. Room 58 has the same layout: 790 is the face with the cutout, 793–795 are the eyes and 791/792 are complete faces.

**What the game does.** Script 68 (`+0x00FE`) runs `loadRoom(56); drawObject(779); drawObject(782); breakHere`. The blink loop then draws 783, 784, 783, 782. Script 108 has the same sequence. Script 86 does the same for Room 58: 792, then 791, then `790; 793`, then a blink cycle.

In ScummVM, `o5_drawObject` only calls `addObjectToDrawQue`. Each frame, `scummLoop_handleDrawing` runs `redrawBGAreas()` when needed; that ends in `drawRoomObjects`, which paints active objects in reverse slot order, so the first directory entry ends up on top. It then runs `processDrawQue()`, which paints the queued objects in call order. So the first frame shows the face painted over the eyes and then the eyes painted over the face: face with eyes. `o5_setState` marks the object rectangle dirty and **clears the draw queue**.

**What the app does.**

1. Neither room's entry script draws anything, so a catalog visit leaves every image inactive. `ShowUnresolvedArtwork` picks the first image at each position that does not overlap an active one. It chooses 779 or 790, then skips the eyes because they intersect the face. The result is the black eye slot.
2. Even when both are active, `RefreshRoomPreview` paints from the end of the directory toward the start. The face is slot 1, so it is painted last and covers the eyes.

See [draw-order-evidence.png](../.verification/archive/audit-2026-09-27/draw-order-evidence.png). The left column shows the app's result and the right column shows the script order.

## Finding 2: Room 87 vs Room 86 (object inside an object)

- **Room 87:** objects 929–931 share one rectangle, (216,56,56,16). The entry script is `drawObject(929)`. Script 93 cycles 930 → 931 → 930 → 929. The background under that rectangle is 100% black, so `CanShowBackground` should not offer a "hide" step. From the data alone, nothing here should go black. If the symptom really is in 87, it needs a repro in the app.
- **Room 86 (the likely one):** 918, 921 and 925 are exact 112×80 peers.
  - 921 (swan) has a 100% black cutout at (152,64,16,16), which 922–924 fill.
  - 925 (volcano) has a cutout at (136,40,48,56) for 926–928, and also contains the eye rectangle.
  - Script 111 draws 925, then starts local script 202, which draws 926, 927 and 928 in a loop. Local script 201 draws 921, then 922.
  - The directory lists the containers first, so the app always paints them over their inserts.
  - Cycling 918 → 921 → 925 also leaves 922 (not an exact peer) active under whatever container is shown.

**How widespread.** A container image with a ≥95% colour-0 cutout exactly under a smaller object appears in rooms **19, 38, 46, 53, 56, 58 and 86** ([cutout-scan.txt](../.verification/archive/audit-2026-09-27/cutout-scan.txt)). Room 46 is the counter-example that rules out a static "insert above container" rule. Its entry script chooses between an open door (`setState(686,0)`, then draw 687 and 688) and a closed door (`drawObject(686)`, which must cover them). Only a call-order model handles both cases.

## Finding 3: Room 17 (existing open item)

The four background holes are the rectangles of objects 354, 355, 359 and 360, which also carry the alternatives 363–366. The entry script branches on `Var[112] == 70`, `Var[171] < 5 / < 8` and `Var[113] == 345` to start local script 203, 204 or 202. Each of those draws four images, one per hole. In a catalog visit these variables are unknown, so no arm runs. The estimate does not run either, because at least one other image is already active. See [loom-17_entry.txt](../.verification/archive/audit-2026-09-27/loom-17_entry.txt).

## Finding 4: Indy3 EGA dialogue choices

**How Indy3 presents choices.** Choices are verbs 120–123, with 124 "Ofrece un objeto" and 125 "Da un puñetazo". Each is set with `verbOps(n, [on, name "…"])`. The script then clears `Var[114]`, loops on `breakHere` until the player picks a verb, and branches `if (Var[114] == 121) { print(...) }`. See the castle guard, script 70, in [indy3-g070-indy-rules.txt](../.verification/archive/audit-2026-09-27/indy3-g070-indy-rules.txt).

**Why they go missing.** ScummVM special-cases `GID_INDY3` (non-Mac):

| Opcode | LOOM / v4 rule (current decoder) | Indy3 EGA rule |
|---|---|---|
| `0xAE` wait | reads a subopcode byte | **no subopcode**; always "wait for message" |
| `0x3B`/`0xBB` | (v3) waitForActor, no operand in LOOM | waitForActor with a **byte/var** parameter |
| `0x43`/`0xC3`, `0x23`/`0xA3` getActorX/Y | word parameter | **byte** parameter |

All 16 scripts that set literal choice labels (on verbs 120–123) reach one of these opcodes before their first label, so decoding goes out of sync before any choice is read. A measurement over all 1,010 Indy3 EGA script blobs, using `descumm` in LOOM mode (`-3`) and Indy mode (`-n`) as stand-ins for the current and corrected rules:

| | LOOM rules | Indy3 rules |
|---|---|---|
| Literal verb labels | 66 (53 distinct) | **245 (222 distinct)** |
| `print` lines with literal text | 399 | **862** |
| Scripts with desync markers | 147 | 0 (2 false positives from the word "ERROR" in game text) |

`descumm` is a proxy for the current decoder, so the app's exact counts will differ. Its operand rules for these opcodes match `LoomScriptReader`.

## Recommended next steps (in order, each bounded)

1. **Game-variant opcode rules (Indy3).** Pass the `GameId` into `LoomScriptDisassembler` and apply the four Indy3 differences above. Remove the dead `0x3B` branch and give LOOM the no-operand form. Add regression tests using script 70 (`0xAE` directly followed by `0x38`). Re-run the Indy text extraction and record the new counts.
2. **Indy3 choice sets in the conversations view.** Group consecutive `verbOps` label changes on verbs 120–125 into a *choice set*. Detect the `Var[114] = 0` / wait loop / `if (Var[114] == n)` structure, attach each label to the `print` lines in its branch, and show them as "Indy: *label* → reply". Label this as static structure, not a played transcript.
3. **Call-order renderer (LOOM).** Replace the fixed reverse-directory paint in `RefreshRoomPreview` with the engine model: `paint = drawRoomObjects(directory order, active) + drawQueue (call order since the last redraw)`. `drawObject` appends to the queue; `setState` and room entry clear it. Keep `HitTest` in the same z-order, and treat an inspection click as a `drawObject`. This fixes 56, 58 and 86 whenever the state has been reached, and keeps Room 46 correct.
4. **Evidence-based opening frame for cutscene rooms.** Rooms 56, 58, 86 and 87 are only entered by a global script (`loadRoom(n)` followed by `drawObject` calls). Use the draws between the `loadRoom` and the first frame break (or the first `drawObject` batch) as that room's labelled "opening frame" instead of the generic estimate.
5. **Cutout-aware estimate fallback.** When filling a 100%-colour-0 background hole or container cutout, recursively add the first exact-rectangle insert, and fill per hole instead of all-or-nothing. This addresses Room 17 and gives a sane fallback elsewhere. Keep the "estimate" label.

## Method and limits

- The Python reader re-implements the old-v3 EGA strip decoder and the room directory, and matches the app's rules (including the shared-image-pointer rule). Scripts were taken from the room directory (entry `0x1B`, exit `0x19`, local-script table) and from the `00.LFL` script directory, then disassembled with `descumm` (`-3 -u` for LOOM, `-n -u` for Indy3).
- ScummVM references: `script_v5.cpp` (`o5_drawObject`, `o5_setState`, `o5_wait`, `o5_getActorX/Y`), `script_v3.cpp` (`o3_waitForActor`), `object.cpp` (`drawRoomObjects`, `processDrawQue`), `gfx.cpp` (`redrawBGAreas`) and `scumm.cpp` (`scummLoop_handleDrawing`).
- The app's behaviour in findings 1–3 is inferred from the code. The next implementation session should confirm it in the WPF render harness before and after the fix.
