## Addendum: thumbnails and first-visit builds (coordinator hypotheses, same day)

The user's parallel-stacks snapshots showed a worker in `LoadRoomCardThumbnailsAsync` -> `ReadFirstVisit` -> `ManiacFirstVisit.Run/Prepare` -> `AdvanceFrame` -> `Snapshot`. Checked:

- The pipeline is one sequential pass over the 53 rooms started when the game opens (`PopulateRoomCards`, one `Lazy` per room in `RoomPreviewScenes`); nothing in the hover path (`PlayScreenImage_MouseMove`, `UpdatePlayOverlayHover`, `RefreshPlayOverlays`, `LightHotspotRow`, `Highlight`) reaches `ReadFirstVisit`, `PopulateRoomCards` or the room-card code (grep; `ReadFirstVisit` has two callers, both in `Task.Run`, no `.Value`/`.Result`/`.Wait` of it on the UI thread).
- Measured with a temporary counter in `ScummRoomFirstVisit.Run` (removed again): 53 runs by the time the user's steps were done, **0 additional runs during 3,000 hover moves in On hover** (`out-counts`, not kept). Each room's `Prepare` takes about 0.65 s (53 rooms in 37 s headless) and a live hover loop on the main thread running at the same time stayed at 4.8 ms mean, 31 ms worst per iteration with the whole pipeline running in parallel (no blocking, no growth). So the pipeline is a bounded ~40 to 60 s of background CPU after opening a game, not a per-hover job, and not an unbounded loop (`Prepare` is capped at 300 + 5,000 frames).
- Still open: the user's UI thread was blocked for minutes with 1% CPU; a wait that only exists on the user's machine (saved view options, Roland sound, rendering/GPU) is not excluded. A dump taken during a freeze (Rider/Task Manager) with the UI thread's stack is the next piece of evidence.

## Addendum 2: system-wide freeze (whole desktop, only the hardware pointer moves, no Event Viewer entries)

Off screen, 3,500 synthetic enter/leave moves, `out-gdi-Hover` against `out-gdi-Always` (not kept): GDI objects 35 to 27 (Hover) and 35 (Always), USER objects 55 to 38 and 52 to 46, handles 1533 to 1422 and 1506 to 1443, threads 32 to 25 and 32 to 28, private bytes 500-550 MB both, visual-tree size 619-620 in both: **nothing grows with enters in either mode**. Off-screen windows may not be composited by DWM, so this does not cover the graphics driver.

Calls reachable from the Hover pointer path (`PlayScreenImage_MouseMove`, `UpdatePlayOverlayHover`, `RefreshPlayOverlays`, `DrawHotspotBox`, `LightHotspotRow`): new `Border` and two unfrozen `SolidColorBrush` per redraw (also per frame under Always), a new `RectangleGeometry` clip per redraw, `Canvas.Children.Clear/Add`; no `Effect`, `BitmapCache`, `RenderTargetBitmap`, popup/tooltip creation, animation or timer. Source search of `src` for low-level hooks, raw input, `ClipCursor`, `BlockInput`, `ShowCursor`, `timeBeginPeriod`, thread or process priority, spin waits, `CompositionTarget.Rendering`, `CreateCursor`/`SetCursor`: none exist (the only P/Invoke is `GetDoubleClickTime`; the only `CaptureMouse` is a scroll button at xaml.cs:2881). The cursor over the play image is `Cursors.None` set each frame (also under Never). The sound stack is not touched by the pointer path (sounds follow the frame timer, `_sceneSound.Update`, in every mode). What differs Hover vs Always: Hover redraws the canvas when the pointer cell changes and draws one strong box; Always draws all boxes each frame.

## Addendum 3: render cost (user: window resize is slow, sound device has no effect, single display, NumLock still toggles during the freeze)

XAML/code review of the main window: no `Effect`, `BlurEffect`, `DropShadowEffect`, `BitmapCache`/`CacheMode`, `OpacityMask`, `VisualBrush` or opacity animation anywhere in `src` (one `Opacity="0"` hover shade inside a button template, one forever `DoubleAnimation` on the busy spinner at xaml.cs:3021 while busy). Every pixel-art image (play screen, room preview, overlays, verb strip) uses `BitmapScalingMode.NearestNeighbor`; only the 200x42 title image uses `HighQuality`. `AllowsTransparency` appears only on popups (menus, combo drop-downs), each created when opened. The 53 room cards are plain `Button`s in a `WrapPanel` (not virtualized, but small bitmaps). No software-only render mode is set.

Measured off screen (`LiveHover ... render`, `out-render/live.txt`), whole `MainWindow` into a `RenderTargetBitmap`, pointer on the sign, median of 6 renders: 1280x800 6.4 / 6.5 / 6.6 ms (Hotspots Never / On hover / Always); 1920x1080 10.0 / 11.6 / 10.6 ms; 2560x1440 15.3 / 15.7 / 14.6 ms. `ShowPlayFrame` (compose the 320x200 screen, write the bitmap, overlays) costs 2.6 to 3.2 ms per frame at every size and mode (about 2.4 ms of that is `Compose`, the same at all sizes because the image is composed at native size and scaled by WPF). **On hover costs the same as Never and Always**, nothing grows with window size except the scaled-image render, and nothing in the main window is expensive on the CPU side. Nothing was changed: no waste large enough to explain a minutes-long desktop stall was found, so there is no before/after. Possible later saving (not done, no evidence it matters): skip `Compose` + `WritePixels` on frames where the session changed nothing visible.

The slow window resize reported by the user is not seen here (off-screen layout/render of the whole window at 2560x1440 is 15 ms); it may be the GPU path (hardware rendering of the stretched image through the DWM on that machine), which an off-screen CPU-side `RenderTargetBitmap` does not exercise. The `DisableHWAcceleration=1` test above separates the two.
